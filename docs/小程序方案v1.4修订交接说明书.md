## 一、项目现状（必须先了解）

### 1.1 项目是什么

**退运智录（ReturnVision）**：拍照识别快递面单 -> 双引擎交叉验证 -> DeepSeek LLM 分析 -> 人工确认 -> 写入飞书多维表格。

- 上线地址：https://returnvision.jxing.tech
- 现有前端：Vue 3 + Element Plus 的 PC 工作台（运营/管理员用）
- 后端：Java 21 + Spring Boot 3.x + MyBatis-Plus + MySQL 8.0
- 现在要做：**新增微信小程序端**，给现场仓储人员拍照录入用

## 二、方案演进历程（理解为什么是现在这样）

方案经过 5 轮讨论演进，你必须理解这个历程，否则会重复前一个 AI 的错误：

### 2.1 v1.0（初版）

- 技术选型：uni-app + WebSocket + 策略 A（绑定已有账号）
- 主体：待定
- 问题：多个事实性偏差（表名错、SecurityConfig 漏配、WS 路径不一致等）

### 2.2 v1.1（修复审查问题）

- 修复 5 个事实性偏差
- 补设计缺口（心跳/重连/持久化/轮询降级）
- 砍掉双主题（仅浅色）
- **仍用策略 A + 自助绑定（bind_token）**

### 2.3 v1.2（确定自助绑定）

- 小程序端仅微信登录，不显示飞书登录
- 自助绑定（模式 B）：未绑定返回 bind_token，用户输账号密码绑定
- 补 bind_token 安全设计

### 2.4 v1.3（扩写持久化）

- 扩写任务持久化权衡（内存方案）
- **此时方案仍是策略 A + 企业主体**

### 2.5 v1.4 的转向（关键！）

用户提出两个想法，彻底改变了方案：

1. **"飞书应用能不能让用户自己绑定？"** -> 多租户需求浮现
2. **"微信小程序能不能就用策略 B？"** -> 想用个人主体发布

经过讨论发现：
- 多租户需要管理员配置飞书密钥 -> 产生不了管理员（策略 B 自动建号都是 STAFF）
- 但**用户提醒"我们不是还有 PC 端吗"** -> 管理员走 PC 端，小程序不用管管理员
- 于是：**策略 B + 邀请码 + 个人主体 + 多租户** 成立
- 邀请码替代了 bind_token，更安全（不暴露 app-secret）、可控（可过期/限次）

**这就是 v1.4 的来由。你要落实的就是这个最终方案。**

## 四、v1.4 最终方案（你要落实的目标）

### 4.1 方案总览

```
主体：个人主体（开发期 + 发布都用，邀请码解决审核）
登录：策略 B（openid 自动建号，任何微信用户可进）
准入：邀请码（绑公司，可过期/限次/失效；未绑公司不能录入）
多租户：feishu_config 表，按用户所属公司选飞书凭证
管理：PC 端管配置/邀请码/用户，小程序只做录入
推送：WebSocket（替代 SSE，PC 端 SSE 不动）
视觉：源力 token 仅浅色
上传：新增 /api/upload/async（小程序用），PC 端 /api/upload 不动
```

### 4.2 核心流程

#### 4.2.1 注册流程（首次进小程序）

```
1. 用户打开小程序 -> wx.login 拿 code
2. POST /api/auth/wx-login {code}
3. 后端换 openid -> 查 sys_user.wx_openid
   - 已存在且 feishu_config_id 非空：签发 JWT（含 feishuConfigId），登录成功，正常进入
   - 已存在但 feishu_config_id 为空（注册过但没输邀请码）：签发 JWT（feishuConfigId=NULL），返回 {need_invite: true}
   - 不存在：自动建号（username=wx_{openid后8位}, role=STAFF, status=active, wx_openid=openid, feishu_config_id=NULL）
     -> 签发 JWT（feishuConfigId=NULL）
     -> 返回 {need_invite: true}
4. 前端收到 need_invite -> 跳邀请码输入页
5. 用户输邀请码 -> POST /api/auth/wx-register {invite_code}
6. 后端校验码（未过期/未用尽/未失效）-> 拿到 feishu_config_id -> 写入 sys_user.feishu_config_id
   -> 重新签发 JWT（含 feishuConfigId）
7. 进入正常使用
```

#### 4.2.2 拍照录入流程

```
1. 拍照（uni.chooseMedia）-> 压缩（uni.compressImage，500KB 内）
2. POST /api/upload/async（带 JWT）-> 返回 taskId
3. uni.connectSocket(wss://.../ws/upload?access_token=xxx)
4. send {action:subscribe, taskId} -> 接收 step 事件（时间线展示）
5. 收到 result 事件 -> 展示识别结果
6. 用户编辑确认 -> POST /api/confirm -> 后端按 user.feishuConfigId 查凭证 -> 写对应飞书表格
```

#### 4.2.3 管理流程（PC 端）

```
1. 管理员登录 PC 端（账号密码/飞书 OAuth，已有）
2. 配置多家公司的飞书密钥（feishu_config 表 CRUD）
3. 为每家公司生成邀请码（invite_code 表，绑 feishu_config_id）
4. 把邀请码发给对应公司仓储人员
5. 员工用邀请码注册后，管理员可在 PC 端用户管理看到
```

#### 4.2.4 审核流程（发布过审用）

```
审核员（新微信）打开小程序：
  -> 自动建号 -> need_invite
  -> 提示输邀请码
  -> 审核员用"体验邀请码"（写在小程序介绍里，绑测试公司配置）
  -> 进入完整流程，写入测试飞书表格
  -> 过审
```

## 五、第 6 点风险表问题的解决方案（用户特别要求说清楚）

### 5.1 问题描述

v1.3 风险表（[docs/13](./13-微信小程序方案设计.md) 约第 569-570 行）写：

> - 登录策略 A 依赖企业主体
> - 若最终用个人主体，策略 A 不可用

审查者质疑：策略 A 是"首次微信登录绑定已有账号"，已有账号是 sys_user，可通过管理员手动创建或飞书 OAuth 创建，**技术上不依赖小程序主体**。个人主体小程序也能 wx.login 拿 openid 绑定已有 sys_user。这条风险的逻辑链不清。

### 5.2 真相：原表述确实有误

**前一个 AI 确认：这条风险表述有误，审查者说得对。**

拆解逻辑链：

| 策略 A 的步骤 | 依赖什么 | 依赖企业主体吗 |
|--------------|---------|--------------|
| wx.login 拿 code | 微信小程序 AppID | 个人主体也能拿 AppID，**不依赖** |
| code 换 openid | code2session 接口 | 个人主体可用，**不依赖** |
| openid 查 sys_user | sys_user 表有数据 | sys_user 可管理员手动建，**不依赖** |
| 绑定 openid 到 sys_user | 写 wx_openid 字段 | 纯 DB 操作，**不依赖** |
| 签发 JWT | 现有鉴权体系 | **不依赖** |

**结论：策略 A 技术上完全不依赖企业主体。** 个人主体小程序技术上能跑通整个策略 A。

### 5.3 前一个 AI 当初为什么写错

前一个 AI 混淆了两条线：

1. **真正的企业主体依赖**其实在策略 B：策略 B（openid 自动建号）在个人主体审核时，"无感知注册"逻辑易被质疑，这条才和企业主体相关
2. **审核合规 vs 技术依赖被混淆**：策略 A 在个人主体下技术能跑，但"要求用户预有账号"在面向公众的个人主体审核时，审核员新微信登不进去会暴露"内部工具"属性被卡——这是**审核风险**，不是**技术依赖**

前一个 AI 把"审核合规"错写成"技术依赖"，导致逻辑链不清。

### 5.4 v1.4 的解决方案：直接删除

**v1.4 放弃策略 A，改用策略 B + 邀请码。** 因此：

- "策略 A 依赖企业主体"这条风险**整体删除**（不再用策略 A，无存在意义）
- "若用个人主体，策略 A 不可用"这条风险**整体删除**（同上）
- 替换为 v1.4 新方案的真实风险（见 5.5）

## 十三、.env 处理与 FeishuService 改造方案（部署侧补充）

> v1.0 遗漏：未说明 .env 硬编码飞书配置如何处理。本节补充。

### 13.1 现状

飞书凭证链路：`.env（FEISHU_APP_ID/SECRET/TOKEN/TABLE_ID）→ docker-compose env_file 注入 → application.yml（feishu.app-id: ${FEISHU_APP_ID}）→ @Value 注入 FeishuService 构造器 → 全局单例，所有用户共用一套凭证`。

FeishuService 是 `@Service` 单例，凭证在构造时注入运行期不可变，`cachedToken/tokenExpireAt` 单例字段缓存 tenant_access_token。

### 13.2 与多租户的冲突

| 维度 | 现状（单租户） | v1.4 多租户要求 |
|------|--------------|----------------|
| 凭证来源 | .env 环境变量 | feishu_config 表 |
| 凭证数量 | 1 套 | N 套（每公司一套） |
| 注入时机 | 构造时（@Value） | 运行时（按 user 查） |
| FeishuService 形态 | 全局单例，字段不可变 | 凭证作方法参数，token 按 configId 缓存 |

### 13.3 方案：保留 .env 作"默认/主公司"配置 + feishu_config 表存多公司

**理由**：平滑过渡（现有部署不破坏）、避免冷启动（全删 .env 后 feishu_config 表空系统跑不起来）。

**application.yml 改造**（feishu.* 保留，语义改为默认，允许空）：
```yaml
feishu:
  app-id: ${FEISHU_APP_ID:}        # 默认/主公司配置，可空（空时走 feishu_config 表）
  app-secret: ${FEISHU_APP_SECRET:}
  app-token: ${FEISHU_APP_TOKEN:}
  table-id: ${FEISHU_TABLE_ID:}
  bot-webhook: ${FEISHU_BOT_WEBHOOK:}
```

**FeishuService 改造**（凭证从构造时注入改为方法参数 + token 按 configId 缓存）：
- 凭证不再作 `private final` 字段，改为 `writeRecord` 方法参数接收 `FeishuConfig` 对象
- token 缓存从 `cachedToken/tokenExpireAt` 单例字段改为 `Map<Long/*configId*/, TokenCache>` 按 configId 隔离，避免跨租户串号
- 新增 `FeishuConfigService`（或 Mapper）按 configId 查库拿凭证
- app_secret 加密存储：需新增 AES 加解密工具类（项目当前无，grep 未发现），PC 端管理界面不回显明文

**调用方改造**（UploadController.confirmSingle L728-747）：
- 取记录的 feishu_config_id（见十五节断层 3/4）
- null 时用 .env 默认配置（PC 端平台 ADMIN 兜底）
- 非空时查 feishu_config 表拿凭证，传给 writeRecord

**.env.example 注释更新**：标注"默认/主公司配置，多租户扩展后其他公司走 feishu_config 表"。

### 13.4 编码阶段必做

1. token 缓存隔离（最高优先）：`Map<configId, TokenCache>`，否则跨租户串号
2. PC 端兜底（高优先）：`configId = user.feishuConfigId != null ? user.feishuConfigId : defaultConfigId`
3. app_secret 加解密（中优先）：新增 AES 工具 + 管理界面不回显
4. schema.sql 预置一条主公司 feishu_config 行（值与 .env 一致），或 application.yml 配 `feishu.default-config-id`

## 十四、用户隔离方案（多公司多管理员）

> v1.0 遗漏：未说明多公司管理员如何隔离。本节补充。

### 14.1 问题

多公司用系统时，A 公司管理员应该只管 A 公司的用户/邀请码/飞书配置，不能管 B 公司的。现状 sys_user 的 feishu_config_id 只给小程序 STAFF 绑公司用，ADMIN 是平台级不绑公司，接口没有按公司过滤。

### 14.2 方案：feishu_config_id 适用所有角色，区分平台管理员和公司管理员

不引入新角色，用 feishu_config_id 区分：

| 角色 | feishu_config_id | 能管什么 | 凭证来源 |
|------|------------------|---------|---------|
| 平台 ADMIN | null | 所有公司，平台运维 | .env 默认配置 |
| 公司 ADMIN | 非空（绑某公司） | 只管自己公司 | DB feishu_config |
| 公司 SUPERVISOR | 非空 | 只看自己公司记录 | 同上 |
| 公司 STAFF | 非空 | 只看自己记录 | 同上 |

### 14.3 接口隔离规则

| 接口 | 平台 ADMIN（null） | 公司 ADMIN（非空） |
|------|-------------------|-------------------|
| /api/admin/users | 看所有用户 | 按 feishu_config_id 过滤只看自己公司 |
| /api/admin/feishu-config | CRUD 所有 | 只能看自己的（不能改） |
| /api/admin/invite-code | 看所有 | 按 feishu_config_id 过滤 |
| /api/records | 看所有 | 按 feishu_config_id 过滤（SUPERVISOR/ADMIN 看本公司，STAFF 看自己） |

实现方式：接口层根据当前用户 feishu_config_id 加 WHERE 条件。null 时不加过滤（看所有），非空时按 feishu_config_id 过滤。

### 14.4 冷启动链路（解决鸡生蛋）

```
平台 ADMIN（AdminInitializer 创建，admin/admin123，feishu_config_id=null，用 .env 默认配置）
  → 创建第一个 feishu_config（公司 A 配置）→ /api/admin/feishu-config POST
  → 生成邀请码（绑公司 A feishu_config_id）→ /api/admin/invite-code POST
  → 平台 ADMIN 在 PC 端用户管理手动创建公司 A 管理员账号（username/password/feishu_config_id=公司A/ADMIN 角色）
  → 公司 A 管理员登录 PC 端，可管自己公司用户/邀请码
```

> 公司管理员**不通过小程序邀请码注册**（邀请码只绑公司不指定角色，小程序注册都是 STAFF）。公司管理员由平台 ADMIN 在 PC 端手动创建（账号密码 + feishu_config_id + ADMIN 角色）。

## 十五、业务链条断层与方案

> v1.0 遗漏：未做端到端业务链条梳理。本节列出 6 个断层及方案。

### 15.1 断层清单

| 断层 | 描述 | 影响 | 方案 |
|------|------|------|------|
| 1 | 公司管理员创建流程未明确 | 邀请码只绑公司不指定角色，小程序注册都是 STAFF，公司管理员（ADMIN）怎么来？ | 平台 ADMIN 在 PC 端手动创建公司管理员（账号密码 + feishu_config_id + ADMIN 角色） |
| 2 | 接口按 feishu_config_id 过滤逻辑未明确 | /api/admin/users、/api/admin/invite-code、/api/records 没有按公司隔离 | 接口层根据当前用户 feishu_config_id 加 WHERE 条件（见十四节） |
| 3 | return_records 缺 feishu_config_id 字段（关键断层） | 多租户数据隔离断链，无法按公司过滤记录 | return_records 加 feishu_config_id 字段（BIGINT，可空），记录创建时写入=创建者 user 的 feishu_config_id。DDL 变更加到 schema.sql + docs/05 |
| 4 | confirm 按记录 feishu_config_id 还是用户 feishu_config_id 查凭证 | 用户换公司后旧记录应写到旧公司飞书表，不是新公司 | confirm 按记录的 feishu_config_id 查凭证（断层 3 加的字段）。null 用 .env 默认。feishu_config.status=disabled 返回 2005 |
| 5 | 员工换公司流程未明确 | feishu_config_id 要改，谁改、怎么改没说 | 平台/公司 ADMIN 在用户管理改 feishu_config_id。员工不能用邀请码自己换公司（避免随意换）。旧记录 feishu_config_id 不变 |
| 6 | 飞书 OAuth 用户绑 feishu_config_id 流程 | 飞书 OAuth 创建 sys_user 没有 feishu_config_id | 公司管理员先飞书登录一次（创建 sys_user，feishu_config_id=null, role=STAFF）→ 平台 ADMIN 改 feishu_config_id + 角色 |

### 15.2 关键断层详解：断层 3（return_records 加 feishu_config_id）

**现状**：return_records 表有 created_by（user_id，F03 操作审计加的），没有 feishu_config_id。查询"公司 A 的记录"要 join sys_user 按 feishu_config_id 过滤，多一次 join 慢且复杂。

**方案**：return_records 加 feishu_config_id 字段（BIGINT，可空），记录创建时写入=创建者 user 的 feishu_config_id。

```sql
ALTER TABLE return_records ADD COLUMN feishu_config_id BIGINT COMMENT '所属飞书配置（NULL=平台级，按公司隔离用）';
CREATE INDEX idx_return_records_feishu_config ON return_records(feishu_config_id);
```

**连带影响**：
- buildRecord（UploadController L1000）要加 feishu_config_id 字段
- confirmSingle（L728）按记录的 feishu_config_id 查凭证（不是当前用户的）
- /api/records 接口按 feishu_config_id 过滤（不 join sys_user）

### 15.3 业务链条完整梳理（6 条链路）

**链路 1：多租户冷启动**
平台 ADMIN（AdminInitializer）→ 创建 feishu_config → 生成邀请码 → 平台 ADMIN 手动创建公司管理员账号（断层 1）→ 公司管理员登录 PC 端

**链路 2：公司管理员管理**
公司管理员登录 → 查看本公司用户（断层 2）→ 生成邀请码 → 查看本公司记录（断层 3）

**链路 3：仓储员工小程序使用**
微信登录 → 自动建号（STAFF, feishu_config_id=null）→ 返回 need_invite → 输邀请码 → 绑 feishu_config_id → 重新签发 JWT → 拍照 → /api/upload/async → WebSocket 推送 → 编辑确认 → /api/confirm（按记录 feishu_config_id 查凭证，断层 4）→ 写对应公司飞书表

**链路 4：员工换公司**
平台/公司 ADMIN 改 feishu_config_id（断层 5）→ 旧记录 feishu_config_id 不变仍写旧公司飞书表

**链路 5：平台 ADMIN 写飞书**
平台 ADMIN（feishu_config_id=null）确认记录 → 按记录的 feishu_config_id 查凭证 → null 用 .env 默认 → 写对应公司飞书表

**链路 6：飞书 OAuth 公司管理员登录**
公司管理员飞书 OAuth 登录（用 .env 平台级 client-id）→ 创建 sys_user（feishu_config_id=null）→ 平台 ADMIN 改 feishu_config_id + 角色（断层 6）
