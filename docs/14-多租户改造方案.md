# 14 - 多租户改造方案

---

## 〇、文档定位

退运智录（ReturnVision）原为单公司工具，飞书凭证全局单例（.env → @Value → FeishuService）。现需支持**多公司使用**，每家公司有自己的飞书应用配置，数据按公司隔离。

本文档定义多租户改造的**数据库变更、FeishuService 改造、用户隔离、用户注册机制、业务流程、接口变更**，作为后续编码的依据。

**核心原则**：
- 只做多租户改造 + 用户隔离 + 用户自助注册，不做小程序端（已取消）。
- 平滑过渡：.env 保留作默认主公司配置，现有部署不破坏。
- PC 端已有上传/SSE/确认链路不改，只改 FeishuService 凭证查询方式。
- 用户自助注册：公司管理员自助注册（飞书应用验证），普通用户用注册码注册，平台 ADMIN 不需手动创建每个用户。

|------|------|

### 3.2 FeishuService 改造

**现状**：全局单例 + @Value 凭证 + 单例 token 缓存。

**改造后**：

| 项 | 现状 | 改造后 |
|----|------|--------|
| 凭证来源 | .env @Value 注入 | 方法参数接收 FeishuConfig 对象 |
| 凭证字段 | private final appId 等 | 删除，改为方法参数 |
| token 缓存 | cachedToken/tokenExpireAt 单例字段 | `Map<Long/*configId*/, TokenCache>` 按 configId 隔离 |
| writeRecord 签名 | `writeRecord(data, imageUrl)` | `writeRecord(data, imageUrl, FeishuConfig config)` |
| 凭证查询 | 无 | 新增 FeishuConfigService 按 configId 查库 |

**writeRecord 改造伪代码**：
```java
public String writeRecord(Map<String, Object> recordData, String imageUrl, FeishuConfig config) {
    if (config == null || config.getAppId() == null) {
        config = getDefaultConfig();  // 兜底：用 .env 默认配置（PC 端平台 ADMIN）
    }
    String token = getTenantAccessToken(config);  // 按 configId 缓存
    // 组装字段 + 调 Bitable API（逻辑不变）
}
```

#### 3.2.1 token 缓存并发模型（v1.4 决策）

`getTenantAccessToken` 的 `computeIfAbsent` 在高并发下若多线程同时 miss，会重复调飞书 token 接口（飞书有 QPS 限制）。改用 `ConcurrentHashMap<Long, CompletableFuture<TokenCache>>`：

```java
private final ConcurrentHashMap<Long, CompletableFuture<TokenCache>> tokenCache = new ConcurrentHashMap<>();

private String getTenantAccessToken(FeishuConfig config) throws Exception {
    CompletableFuture<TokenCache> future = tokenCache.computeIfAbsent(config.getId(),
        k -> CompletableFuture.supplyAsync(() -> fetchNewToken(config)));
    TokenCache cache = future.get();
    if (cache.isExpired()) {
        tokenCache.remove(config.getId());  // 过期则移除，下次重新获取
        return getTenantAccessToken(config);  // 递归一次
    }
    return cache.token;
}
```

**模式依据**：与现有 `AlertService` 的 `ExecutorService` 异步思路一致，团队已熟悉。第一个线程异步 fetch，其余线程 join 同一 Future，避免重复请求。

**配置变更清缓存**（改进点 #5）：`feishu_config` 更新时调用 `tokenCache.remove(configId)`，下次重新获取。

### 3.3 用户隔离

**角色体系**：默认两层（ADMIN + STAFF），SUPERVISOR 保留但默认不分配。

| 角色 | feishu_config_id | 职责 | 凭证来源 |
|------|------------------|------|---------|
| 平台 ADMIN | null | 管所有公司、平台运维、事后禁用恶意公司 | .env 默认配置 |
| 公司 ADMIN | 非空（绑某公司） | 管本公司用户/记录/飞书配置/生成注册码 | DB feishu_config |
| 公司 STAFF | 非空 | 录入退货、确认写飞书 | 同上 |
| SUPERVISOR（可选） | 非空 | 如果某公司需要"主管审核"环节，给某些用户此角色。默认不分配，不影响现有代码 | 同上 |

> 保留 SUPERVISOR 不改现有代码的角色体系（SecurityConfig/权限矩阵），只是默认不分配。如果某公司业务需要审核环节，再给用户 SUPERVISOR 角色。

**接口隔离规则**：

| 接口 | 平台 ADMIN（null） | 公司 ADMIN（非空） |
|------|-------------------|-------------------|
| /api/admin/users | 看所有用户 | 按 feishu_config_id 过滤只看自己公司 |
| /api/admin/feishu-config | CRUD 所有 | 只能看自己的（不能改） |
| /api/records | 看所有 | 按 feishu_config_id 过滤（STAFF 看自己 created_by，ADMIN 看本公司） |

#### 3.3.1 隔离方案选型：租户插件 + @InterceptorIgnore 白名单（v1.4 定稿）

**方案**：用 MyBatis-Plus `TenantLineInnerInterceptor` 对 `return_records`、`sys_user` 表自动加 `feishu_config_id` 条件；后台任务等跨租户场景用 `@InterceptorIgnore(tenantLine="true")` 显式豁免。

**选型理由**（原 v1.3 手动 WHERE 方案废弃）：

| 维度 | 手动 WHERE（v1.3） | 租户插件+白名单（v1.4） |
|------|-------------------|----------------------|
| 遗漏方向 | 漏加 `.eq(feishuConfigId)` | 漏加 `@InterceptorIgnore` |
| 遗漏后果 | 公司 A 看到公司 B 数据（**数据泄露，安全事件，静默不可发现**） | 后台任务只处理 null 租户（**功能错误，可被监控发现**） |
| 安全模型 | 默认全看，显式 opt-in 过滤 | **默认隔离，显式 opt-out 跨租户**（默认安全） |
| 工作量 | 32 处查询点逐一改 + 遗漏风险 | 1 处配置 + 1 个 MetaObjectHandler + 3 处豁免注解 |

**决定性理由**：数据泄露是安全问题且静默不可发现；功能错误会暴露为清理异常可被发现。从安全工程角度，"默认隔离、显式 opt-out"比"默认全看、显式 opt-in"更符合默认安全原则。

**配置**（基于现有 `config/AppConfig.java` 的 `MybatisPlusInterceptor`）：

```java
TenantLineInnerInterceptor tenant = new TenantLineInnerInterceptor(new TenantLineHandler() {
    @Override
    public Expression getTenantId() {
        Long cid = TenantContext.currentFeishuConfigId();
        return cid == null ? null : new LongValue(cid);  // null = 平台 ADMIN，不加条件
    }
    @Override
    public String getTenantIdColumn() { return "feishu_config_id"; }
    @Override
    public boolean ignoreTable(String tableName) {
        // 仅 return_records / sys_user 加租户条件，其他表（feishu_config/register_code/ocr_log 等）不隔离
        return !"return_records".equals(tableName) && !"sys_user".equals(tableName);
    }
});
interceptor.addInnerInterceptor(tenant);  // 必须在 PaginationInnerInterceptor 之前
```

**配套组件**：
- `security/TenantContext.java`：从 SecurityContext 取当前用户 `feishuConfigId`，null 表示平台 ADMIN
- `config/TenantMetaObjectHandler.java`：insert 时自动从 TenantContext 填充 `feishuConfigId`（省去手动 set）
- `@InterceptorIgnore(tenantLine="true")`：标注在 `RetentionScheduler` 的三个清理方法、全局统计查询等跨租户场景

**4 个已知缺点与应对**（自审重点）：
1. **null 语义**：`getTenantId()` 返回 null 时不加条件（平台 ADMIN）。必须写测试验证"null 真的不加条件而非加 `= null`"。
2. **隐式行为**：新人看 SQL 日志会困惑 `feishu_config_id = ?` 来源。本文档 §3.3.1 记录机制。
3. **运单去重**：已确认**同公司去重**，[UploadController L956-965](../returnvision-backend/src/main/java/tech/jxing/returnvision/controller/UploadController.java#L956) 去重查询正常被加租户条件，无需豁免。
4. **插件顺序**：租户插件必须在分页插件**之前** add，否则分页 SQL 不带租户条件。AppConfig 改造时重点验证。

**豁免清单**（必须用 @InterceptorIgnore 显式声明跨租户）：
- `RetentionScheduler.cleanupReturnRecords/cleanupAuditLogs/cleanupOcrLogs`：后台清理所有租户过期数据
- 平台 ADMIN 的全局统计接口（/api/dashboard 全量统计）：平台 ADMIN 的 `getTenantId()` 返回 null 已天然不加条件，无需注解

### 3.5 confirm 凭证查询逻辑

**confirmSingle 改造**（UploadController L728-747）：

```
confirmSingle(recordId, record):
  configId = record.getFeishuConfigId()    // 按记录的公司查凭证（不是当前用户的）
```

### 3.6 用户注册机制

#### 3.6.1 公司管理员注册（自助 + 飞书应用验证）

**流程**：
```
PC 端注册页 → 选择"公司管理员注册"
  → 填写：用户名、密码、公司名称、飞书应用信息（app_id/app_secret）
  → 后端三步验证：
    1. 验证应用凭证：用 app_id/app_secret 调飞书 API 换 tenant_access_token
       POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal
       成功 → 凭证有效；失败 → 返回 2006
    2. 系统自动创建多维表格（飞书 API 支持创建 app + table + fields）
       用 tenant_access_token 创建多维表格 + 标准字段
       成功 → 拿到 app_token/table_id；失败 → 返回 2007
    3. 字段自动创建：系统维护标准字段名列表，创建表格时一并创建
  → 验证通过 → 创建 feishu_config（AES 加密 app_secret）+ sys_user（role=ADMIN, feishu_config_id）
  → 自动通过（无需平台 ADMIN 审核），平台 ADMIN 事后可禁用恶意公司
```

> **方案 B：系统自动创建标准多维表格**。公司管理员只需在飞书开放平台创建应用（拿 app_id/app_secret），注册时系统自动创建多维表格 + 所有标准字段。这样字段名一定合规，不需要手动对齐。
>
> **飞书应用权限要求**：公司管理员在飞书开放平台创建应用时，需开启以下权限范围（scope）：`bitable:app`（多维表格读写）、`bitable:app:table`（表格读写）。否则自动建表会失败（返回 2007）。

**标准字段列表**（系统创建表格时一并创建）：
运单号、收件人姓名、收件人电话、收件人地址、寄件人姓名、寄件人电话、寄件人地址、快递公司、托寄物、退货日期、退货原因、退货分类、图片URL、备注

#### 3.6.2 普通用户注册（注册码 + 直接创建并存）

**两种方式并存，公司管理员按需选择**：

**方式 A：注册码（批量注册）**
```
公司管理员在 PC 端生成注册码（绑自己公司 feishu_config_id）
  → 注册码可配置：有效期、最大使用次数
  → 公司管理员把注册码发给本公司仓储员工
员工在 PC 端注册页 → 选择"普通用户注册"
  → 填写：用户名、密码、注册码
  → 后端校验注册码（未过期/未用尽/未失效）→ 拿 feishu_config_id
  → 创建 sys_user（role=STAFF, feishu_config_id）
  → 注册码 used_count++
```

**方式 B：直接创建（单个添加）**
```
公司管理员在 PC 端用户管理直接创建员工账号
  → 填写：用户名、密码
  → 创建 sys_user（role=STAFF, feishu_config_id=公司管理员的）
```

> 方式 A 用于批量（新公司开户时一次性注册多个员工），方式 B 用于单个（后续新员工入职）。两者并存，公司管理员按需选择。

### 3.7 安全考虑

- **注册接口限流**：防暴力注册（同一 IP 每小时限制 N 次）。**复用现有 `ExportRateLimiter` 模式**（ConcurrentHashMap+AtomicInteger），新建 `RegisterRateLimiter`，key 为 `IP+小时`。不引入 Bucket4j/Resilience4j，保持依赖干净。
- **飞书凭证探测防护**：限制验证失败次数（同一 IP 验证飞书凭证失败 5 次后封锁 1 小时）。单独建 `FeishuVerifyRateLimiter`，复用同一限流模式。
- **app_secret 加密**：AES/GCM 加密存储，PC 端管理界面不回显明文，接口返回 `"******"` 占位
- **注册码泄露**：可过期/限次/撤销，使用记录便于审计
- **密码安全**：强度校验（最少 8 位含字母+数字），BCrypt 哈希存储（现有体系已有）

#### 3.7.1 AES 加密工具（新增 AesCryptoUtil）

项目当前无对称加解密工具（`JwtUtil` 是 HmacSHA 单向签名，`CosClientService` 的 SecretKey 只是字段名），需新建 `common/util/AesCryptoUtil.java`。

| 项 | 方案 |
|----|------|
| 算法 | AES/GCM/NoPadding（带认证标签，比 CBC 安全，防篡改） |
| 密钥来源 | 环境变量 `${AES_SECRET_KEY_V1}`（32 字节 Base64），与 JWT_SECRET/COS_SECRET_KEY 模式一致；轮换时新增 `AES_SECRET_KEY_V2`（见 §3.7.2） |
| 密钥存储 | 只在环境变量，不落库、不入 git；`.env.example` 加占位 |
| IV 生成 | 每次 `SecureRandom` 生成 12 字节 IV（安全红线，自审重点） |
| 存储格式 | `iv:ciphertext:tag`（Base64 拼接） |
| 接口 | `encrypt(plaintext, version) -> "iv:ciphertext:tag"`、`decrypt(payload, version) -> plaintext`（按 version 选密钥） |

#### 3.7.2 AES 密钥轮换（aes_key_version 字段）

环境变量最大的缺点是轮换困难（改密钥需重启，旧密文无法用新密钥解密）。`feishu_config.aes_key_version` 字段缓解此痛点：

- 加密时记录用的密钥版本（写入 `aes_key_version`）
- 解密时按版本选密钥（环境变量支持多版本：`AES_SECRET_KEY_V1`/`AES_SECRET_KEY_V2`）
- 轮换流程：新数据用 V2 加密 → 旧数据按 V1 解密正常工作 → 后台任务逐步重加密迁移到 V2
- 不需要"一次性全量重加密"，可平滑过渡

**密钥泄露爆炸半径评估**：app_secret 泄露的爆炸半径是"只能写该公司的多维表格"，不像数据库密码/支付密钥那样致命，环境变量方案的安全级别足够。

#### 3.7.3 公司禁用后的 JWT 处理（决策）

**不在 `JwtAuthenticationFilter` 加 DB 查询**（每请求查 DB 代价太高），而是在写飞书/录入的关键路径查一次 `feishu_config.status`：

- `confirmSingle` 按 `record.getFeishuConfigId()` 查 `feishu_config` 时顺带检查 status，disabled 抛 2005（已在 §3.5 伪代码）
- `doUploadInternal` 保存记录前查当前用户 `feishu_config.status`，disabled 抛 2005
- 不主动踢人（JWT 无状态），disabled 公司用户"能登录但录不进/确认不了"，配合前端提示跳登录

这是性能与安全的合理折中。

## 四、业务流程

### 4.1 冷启动链路（公司管理员自助注册）

```
平台 ADMIN（AdminInitializer 创建，admin/admin123，feishu_config_id=null，用 .env 默认配置）
  → 登录 PC 端，管所有公司（事后可禁用恶意公司）

公司管理员 → PC 端注册页 → 选择"公司管理员注册"
  → 填写用户名/密码/公司名称/飞书 app_id/app_secret
  → 系统验证飞书应用 + 自动创建多维表格 + 标准字段
  → 创建 feishu_config + sys_user（role=ADMIN, feishu_config_id）
  → 自动通过，可登录 PC 端管本公司
```

### 4.2 公司管理员管理

```
公司管理员登录 PC 端
  → 生成注册码（批量注册员工）或直接创建员工账号（单个添加）
  → 查看本公司用户（按 feishu_config_id 过滤）→ /api/admin/users
  → 查看本公司退货记录（按 feishu_config_id 过滤）→ /api/records
  → 审核确认写入飞书 → /api/confirm（按记录 feishu_config_id 查凭证）
```

### 4.3 仓储员工使用

```
仓储员工登录 PC 端（账号密码，或注册码自助注册）
  → 拍照/上传图片 → /api/upload（同步）或 /api/upload/sse（SSE 流）
  → 双引擎 OCR + 交叉验证 + LLM 分析
  → 人工确认 → /api/confirm → 按记录 feishu_config_id 查凭证 → 写本公司飞书表
  → 查看自己的退货记录（按 created_by 过滤）→ /api/records
```

### 4.4 员工换公司

```
平台/公司 ADMIN 在用户管理改 feishu_config_id
  → 旧记录 feishu_config_id 不变（创建时写入），仍写到旧公司飞书表
  → 新记录按新 feishu_config_id 写到新公司飞书表
```

### 4.5 平台 ADMIN 管理

```
平台 ADMIN（feishu_config_id=null）登录 PC 端
  → 查看所有公司 feishu_config → /api/admin/feishu-config
  → 禁用恶意公司（feishu_config.status=disabled）→ 该公司用户不能录入（2005 错误码）
  → 查看所有用户/记录
  → 确认记录时按记录的 feishu_config_id 查凭证，null 用 .env 默认
```

| 风险 | 影响 | 应对 |

## 十、不引入微服务/Nacos 的决策记录（v1.4）

> 本节记录"是否在本项目引入微服务 + Nacos 配置中心"的决策过程与结论，避免后续重复讨论。

### 10.1 决策结论

**不引入微服务，不引入 Nacos。保持单体 + docker-compose。**

### 10.2 决策依据（代码事实）

| 维度 | 现状 | 微服务要求 |
|------|------|-----------|
| 规模 | 72 个 Java 文件、单容器 | 通常单服务超 10 万行才考虑拆分 |
| 团队 | 单人开发 | 微服务核心收益是"多团队并行"（康威定律） |
| 部署 | 单机 docker-compose | 需 K8s/多机 + 服务网格 + 链路追踪 |
| 运维 | `mvn test` + CI 守门 | 需监控/日志聚合/分布式事务/服务发现 |
| 业务 | 线性录入流程（upload->ocr->llm->confirm） | 微服务适合领域边界清晰的复杂业务 |

### 10.3 微服务的真实代价（单人开发会被吞没）

- 一个 confirm 操作从"本地方法调用"变成"跨服务 HTTP/RPC"，多出网络延迟、超时、重试、幂等性处理
- 分布式事务：confirm 要写本地 DB + 调飞书，跨服务后需 Saga 或最终一致，复杂度暴涨
- 调试：一个请求跨多服务，本地起多进程 + Nacos + 链路追踪，开发体验急剧下降
- 现有 78 个测试全绿、CI 守门的良好状态会被分布式复杂性破坏

### 10.4 Nacos 价值评估

Nacos 两个功能，对本项目的价值：

| 功能 | 对本项目价值 | 结论 |
|------|------------|------|
| 配置中心（动态配置） | 中--多租户后 feishu_config 已在 DB 动态化，Nacos 价值被消解；AES 密钥/限流阈值变更频率低，重启可接受 | 不引入 |
| 服务注册发现 | 低--单服务无需注册发现 | 不引入 |

**关键判断**：多租户改造后最需要动态化的是"每公司的飞书配置"，已放进 `feishu_config` 表。Nacos 解决的"动态配置"痛点被 DB 存 feishu_config 提前消解。

### 10.5 演进路径（按需引入，而非预设）

| 时机 | 动作 | 触发条件 |
|------|------|---------|
| 短期（本次改造） | 保持单体，AES 走环境变量，飞书配置走 DB | - |
| 中期 | 拆"识别服务"（OCR/LLM） | 多公司接入后 OCR/LLM 成 CPU 瓶颈需独立扩容 |
| 中期 | 引 Nacos 配置中心（不引注册发现） | 配置频繁变更成痛点 |
| 中期 | 上负载均衡 + 多实例 | 多机部署需求 |
| 长期 | 真微服务 | 团队 ≥3 人按领域分工 + 单体遇扩容瓶颈 + 有专职运维 |

**原则**：遵循 Martin Fowler"单体优先"原则--绝大多数成功的微服务应用都是从单体演化的，而非一开始就是微服务。让真实数据告诉下一步该拆什么。

### 11.3 实施中发现并修复的缺陷（4 个）

1. **历史数据迁移缺陷**（步骤1）：原方案预置主公司行+UPDATE 迁移，会导致 app_secret 空串->confirm 降级->status=failed 破坏回归。修复：保持 NULL 走 .env 兜底。
2. **token 缓存失败 Future 滞留**（步骤4）：fetchNewToken 失败的 CompletableFuture 留在缓存导致后续无法恢复。修复：whenComplete 异常时移除自身。
3. **ignoreTable null 语义**（步骤6）：getTenantId 返回 null 时 MP 仍加 `=null` 条件导致查询空。修复：ignoreTable 平台级返回 true。
4. **validation 依赖缺失**（步骤7）：项目未引入 spring-boot-starter-validation。修复：DTO 去 validation 注解，Service 层手动校验。

### 11.4 设计边界说明（非缺陷，需知晓）

- **OAuth 登录不在多租户范围**：FeishuOAuthService 仍用平台级 .env 配置换 app_access_token。OAuth 登录是"用飞书账号登录系统"（所有用户共用一个飞书应用），与"写入隔离"（路由到不同公司表格）是两个维度。若未来需"每个公司用自己的飞书应用做 OAuth 登录"，需改造 FeishuOAuthService。
- **注册码 used_count 非原子递增**：当前 select->update，高并发可能超发。测试清单 AT-21 标注 P1。若需严格原子性改 `UPDATE...SET used_count=used_count+1 WHERE used_count<max_uses`。
- **AES 密钥仅支持 V1/V2 两个版本**：AesCryptoUtil 构造器硬编码两个 @Value。若需 V3+ 再加参数。
