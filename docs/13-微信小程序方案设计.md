# 13 - 微信小程序方案设计

---

## 〇、文档定位

退运智录（ReturnVision）现有前端为 Vue 3 + Element Plus 的 PC 工作台，适合运营/管理员在桌面端使用。现场仓储人员需要一个**移动端拍照录入入口**，故新增微信小程序端。

本文档定义小程序端的**技术选型、整体架构、后端增量改动、前端工程结构、用户体系、设计规范沿用、部署与发布前置条件**，作为后续编码与文档细化的依据。

**核心原则**：
- PC 前端不废弃，继续作为后台管理端；小程序作为现场录入端，两者共用同一套后端 API 与设计 token。
- 小程序只做**移动端核心链路**，管理类功能（用户/字典/审计/报表）留在 PC 端。
- 视觉设计语言完整沿用源力（Volcengine）token，保证"同款视觉"。

---

## 一、目标与功能范围

### 1.1 业务目标

为现场仓储人员提供"拍照 -> 识别 -> 人工确认 -> 写入飞书"的移动端入口，替代当前用手机浏览器访问 PC 端的不便。

### 1.2 功能范围（核心链路）

| 功能 | 说明 | 对应 PC 端 |
|------|------|-----------|
| 拍照识别 | 调用原生相机拍照上传，WebSocket 推送处理进度 | RecognitionPanel |
| 人工确认 | 识别结果展示 + 字段编辑 + 确认写入飞书 | RecognitionPanel 确认区 |
| 记录列表 | 查看自己的退货记录，状态徽章展示 | RecordsPanel |
| 记录详情 | 单条记录详情查看 | RecordsPanel 详情 |
| 我的 | 个人信息、退出登录 | ProfilePanel |

**不做**（留在 PC 端）：仪表盘、报表、OCR 统计、用户管理、字典管理、审计日志、数据导出、批量操作。

### 1.3 非目标

- 不做 PC 端功能完整复刻。
- 不做 echarts 图表（包体积与移动端场景不匹配）。
- 不做密集表格（移动端改卡片列表）。
- 不做双主题（小程序端仅浅色，降低复杂度）。
- 不做订阅消息推送（用户关闭小程序后处理完成不主动通知，归入非目标；后续如需再议）。

## 二、技术选型

### 2.1 前端技术栈

| 项 | 选型 | 选型理由 |
|----|------|---------|
| 框架 | uni-app（Vue 3 `<script setup>`） | 语法与现有 PC 前端一致，最大化复用逻辑层与设计 token；一套代码可出小程序 + H5 |
| 构建 | uni-app CLI（Vite 模式） | uni-app 官方推荐 |
| 组件库 | uni-ui / uv-ui + 基于源力 token 自研少量组件（按钮/徽章/卡片） | Element Plus 依赖 DOM，小程序不可用 |

| 相机 | `uni.chooseMedia` | 原生相机，体验优于 PC 端 input capture |
| 存储 | `uni.setStorageSync` | 替代 localStorage |

### 3.2 小程序端上传处理流程（WebSocket 替代 SSE）

```
前端                                   后端
 │── uni.chooseMedia 拍照/选图 ──────────│
 │── uni.uploadFile 上传图片 ──────────►│ /api/upload/async（返回 taskId）
 │◄── 返回 taskId ──────────────────────│
 │── uni.connectSocket(wss://.../ws/upload?token=xxx) ─►│ 握手 + HandshakeInterceptor 校验 token
 │── send {action:"subscribe", taskId} ►│ 订阅指定任务进度
 │◄── push {type:"step", step:1, ...} ───│ 上传COS
 │◄── push {type:"step", step:2, ...} ───│ 双引擎OCR
 │◄── push {type:"step", step:3, ...} ───│ 交叉验证
 │◄── push {type:"step", step:4, ...} ───│ LLM分析
 │◄── push {type:"result", data} ───────│ 处理完成，服务端关闭连接
 │  （断线时自动重连，重连后用 subscribe 拉取已进度）│
```

**事件结构与现有 SSE 完全一致**（含 `type/step/label/status/subSteps/meta` 全部字段），前端时间线 UI 可 1:1 还原 PC 端处理步骤展示。详见 4.3 节事件结构定义。

## 四、后端改动清单

### 4.1 微信授权登录接口（新增）

> 设计对齐现有飞书 OAuth 登录模式（[AuthService.feishuLogin](../returnvision-backend/src/main/java/tech/jxing/returnvision/service/AuthService.java#L215-L247)），保持代码结构一致。

**接口**：`POST /api/auth/wx-login`（需加入 SecurityConfig permitAll 白名单）

**流程**：
1. 前端 `wx.login()` 拿到 `code`，POST 给后端
2. 后端调微信 `code2session` 接口，换 `openid` + `session_key`
3. 按 `openid` 反查 `sys_user.wx_openid`：
   - 已绑定 -> 校验启用 + 查角色 + 生成 JWT（与飞书登录步骤4 完全一致）
   - 未绑定 -> 返回 **1012 错误码**（微信账号未绑定，新增错误码不复用 1004——1004 的 msg 是「飞书账号未绑定，请联系管理员绑定」，微信场景复用会导致 UI 文案违和），msg 提示绑定方式

**响应（已绑定）**：
```json
{ "code": 200, "data": { "access_token": "...", "refresh_token": "...", "user": {...} } }
```

**响应（未绑定）**：
```json
{ "code": 1012, "msg": "微信账号未绑定，请先绑定账号", "data": { "bind_token": "xxx" } }
```

> 小程序端登录页**仅微信登录一个入口，不显示飞书登录**。飞书 OAuth 是网页跳转授权流程，在小程序内跳转体验差且受限，故飞书登录保留在 PC 端，小程序端只用微信登录。

#### 绑定方式：自助绑定

采用自助绑定，用户首次微信登录未绑定时，自行输入账号密码完成绑定，无需管理员介入。

**流程**：
1. `wx-login` 未绑定 -> 返回 1012 + `bind_token`（短期一次性，绑定到 openid）
2. 前端进入绑定页，提交 `bind_token` + `username` + `password`
3. 后端校验 bind_token 拿到 openid，校验密码拿到 sys_user，写入 `wx_openid`，签发正式 JWT

**bind_token 安全设计**：
- 生成：复用 JwtUtil，生成短期 JWT，payload 含 `openid`，有效期 **5 分钟**
- 一次性由 openid 绑定状态保证——绑定成功后 openid 已有归属，同一 bind_token 再来绑定时校验 openid 已被占用而拒绝（已绑定的 openid 再走 wx-login 直接返回 JWT，不会再走 bind）。无需维护 JWT 黑名单，JWT 本身无状态无法主动失效
- 防重放：绑定接口校验 bind_token 未过期 + openid 尚未绑定过（已绑定则拒绝）

**绑定接口**：`POST /api/auth/wx-bind`（需加入 SecurityConfig permitAll 白名单）
- 请求：`{ "bind_token": "xxx", "username": "xxx", "password": "xxx" }`
- 响应（成功）：`{ "code": 200, "data": { "access_token": "...", "refresh_token": "...", "user": {...} } }`
- 响应（密码错误）：`{ "code": 1001, "msg": "用户名或密码错误", "data": null }`（复用现有错误码）
- 响应（bind_token 失效）：`{ "code": 1011, "msg": "绑定凭证已失效，请重新登录", "data": null }`（新增错误码 1011，不复用 1003，避开已被占用的 1008「不能操作自己的账号」）

> 详细请求/响应待补 [docs/06-API接口设计.md](./06-API接口设计.md) 第二章新增小节。

### 4.2 WebSocket 推送通道（新增）

**依赖**：`spring-boot-starter-websocket`（pom.xml 新增）

**端点**：`wss://returnvision.jxing.tech/ws/upload`（路径不带 taskId，连接后用 subscribe 消息订阅）

**鉴权与 Security 配置**：
- `/ws/**` 不在 `/api/` 前缀下，会落到 SecurityConfig 的 `anyRequest().permitAll()`，**握手阶段 Spring Security 不拦截**
- 改由 `HandshakeInterceptor` 在握手前校验 query 参数 `access_token`，校验失败拒绝握手
- 校验通过后将 user 信息存入 WebSocket Session 的 attributes，供后续推送鉴权
- **token 在 URL 的泄露风险与缓解**：access_token 走 query 是因小程序 `uni.connectSocket` 对自定义 header 支持有限，属业界标准做法。但 query 会被 Nginx access_log 记录，需在 Nginx 配置 log_format 过滤 access_token 参数（见 8.1 节），避免 token 落日志文件

**协议**：
- 客户端连接后发送 `{action:"subscribe", taskId:"xxx"}` 订阅指定上传任务进度
- 服务端推送事件（复用现有 SSE 事件结构，含全部字段）：
  - `{type:"step", step:1, label:"上传至云存储", status:"done", subSteps:null, meta:null}`
  - `{type:"result", data:{...识别结果...}}`
  - `{type:"error", msg:"处理失败原因"}`
- 处理完成后服务端主动关闭连接

**心跳与重连**：
- 心跳：客户端每 30s 发 `{action:"ping"}`，服务端回 `{action:"pong"}`；60s 未收到 pong 视为断连
- 重连：客户端自动重连（最多 3 次，间隔 2s/4s/8s 指数退避）
- 重连后重新 subscribe 同一 taskId，服务端从内存任务进度补推已完成的步骤

**任务状态持久化权衡**：

任务进度存储有三种方案：内存（ConcurrentHashMap）/ Redis / MySQL。本项目选**内存方案**。

| 方案 | 存储位置 | 重启后 | 复杂度 | 适合场景 |
|------|---------|--------|--------|---------|
| 内存（选用） | JVM 内 ConcurrentHashMap | 丢失 | 最低 | 短任务、可重试、单机 |
| Redis | Redis 内存 | 不丢失 | 中（引依赖+部署+序列化） | 多实例、长任务、需共享 |
| MySQL | DB | 不丢失 | 高（建表+多次 update） | 强一致、需审计 |

**内存方案工作原理**：
```
taskStore: ConcurrentHashMap<taskId, UploadTask>
  UploadTask = { taskId, userId, currentStep, status, result, createdAt }

1. /api/upload/async 请求进来
   -> 生成 taskId，new UploadTask(status="active") 存进 taskStore
   -> 提交异步线程跑处理链路，立即返回 taskId
2. 异步线程处理：每完成一步更新 task.currentStep 并推 WebSocket
3. 重连/降级：从 taskStore.get(taskId) 读当前进度补推
4. 清理：定时任务每 5 分钟扫一次，删除 createdAt 超 30 分钟的 done/error 任务；active 任务超 5 分钟无进度更新自动转 error（防线程异常卡死）；taskStore 加 maxSize 上限（如 1000），超限拒绝新任务返回"系统繁忙"
```

**重启丢失场景**：
- 处理中重启：taskStore 清空，客户端重连后 `taskStore.get(taskId)=null`，后端推 `{type:"error", msg:"任务已失效"}`，前端提示"处理中断，请重新拍照"
- **关键**：业务数据（return_record）在处理链路中已落 DB（[buildRecord](../returnvision-backend/src/main/java/tech/jxing/returnvision/controller/UploadController.java#L1000-L1035) 只构建实体，`recordMapper.insert` 由调用方执行，见 L184/L296/L797），内存丢的只是"任务进度状态"，不是业务数据。即使识别完重启，用户在"记录列表"仍能看到那条 pending 记录，进详情页继续确认
- **异步链路 insert 时机要求**：`/api/upload/async` 必须复刻同步链路的 insert 时机——COS 上传成功后立即 `recordMapper.insert` 落 status=pending，后续 OCR/交叉验证/LLM 步骤 update 字段。**不能**把 insert 放到所有步骤跑完后，否则重启丢失兜底失效

**取舍逻辑**：
- 丢失代价：单次任务 5-15 秒，并发极低（仓储几人用），重启概率低（发版才重启），丢失后重拍一张照片
- 持久化成本：Redis 要引入依赖+部署容器+序列化；DB 要建表+每步 update（4-5 次写）
- 结论：为应对"一周几次发版、每次最多影响 1-2 个 15 秒任务"引入持久化，复杂度收益比太低

**重连体验**：
```
WebSocket 断连 -> 自动重连 3 次(2s/4s/8s)
  ├─ 任务还在(没重启) -> 补推已进度，用户无感
  └─ 任务失效(重启了) -> 推 error "任务已失效" -> toast 提示重拍
```

**多 Session 订阅同一 taskId**：用户重连时旧 session 可能未断开，出现一个 taskId 多个 session 订阅。策略：**以最新 session 为准**，新连接建立时服务端主动 close 该 taskId 的旧 session（避免重复推送和资源泄漏），客户端无需幂等去重。

**升级触发条件**（满足任一则升级 Redis）：
- 并发任务数 > 50
- 任务耗时 > 1 分钟
- 多实例部署（内存方案不跨实例，负载均衡到另一台找不到任务）
- 发版频率高 + 7x24 使用

> 本项目当前：几人用、任务 15 秒、单实例、发版可控，均不触发升级。升级路径清晰：taskStore 换成 RedisTemplate 操作，接口不变。

**轮询降级**：
- 提供 `GET /api/upload/status/{taskId}` 查询任务当前进度（返回最新 step 状态）
- WebSocket 连续重连 3 次失败后，前端降级为轮询此接口（间隔 2s）
- 降级时不再有实时推送，体验略降但保证可用

**复用现有处理逻辑**：OCR + 交叉验证 + LLM + 落 DB 的 Service 层逻辑完全复用（[UploadController](../returnvision-backend/src/main/java/tech/jxing/returnvision/controller/UploadController.java) 现有 `doUploadInternal` / SSE 里的处理链路），只把"推送出口"从 SseEmitter 换成 WebSocket session。**飞书写入不在异步上传链路内**，仍走现有 `/api/confirm` 共用接口（小程序与 PC 共享，确认时才触发写飞书，对应 `confirmSingle` L737 调用 `feishuService.writeRecord`）。

### 4.3 事件结构定义（与 SSE 1:1 对齐）

现有 SSE 事件由 [UploadController.sendSseEvent](../returnvision-backend/src/main/java/tech/jxing/returnvision/controller/UploadController.java#L870-L884) 生成，字段如下，WebSocket 推送必须包含全部字段：

| type | 字段 | 说明 |
|------|------|------|
| step | `type, step, label, status, subSteps?, meta?` | status: active/done；subSteps: `[{name, status}]`；meta 可选 |
| result | `type, data` | data 为扁平化识别结果（buildFlatResult 输出） |
| error | `type, msg` | 处理失败原因 |

### 4.4 上传接口调整

**现状**：现有 `/api/upload`（[UploadController.upload](../returnvision-backend/src/main/java/tech/jxing/returnvision/controller/UploadController.java#L147-L207)）是"上传即同步处理返回结果"。PC 端 [api.js upload()](../returnvision-frontend/src/api.js#L185-L191) **确实在用此接口**（非假设，已确认）。

**方案**：**不改原接口**，新增小程序专用接口：

- `POST /api/upload/async`：上传图片到 COS，创建处理任务，**立即返回 `taskId`**（不阻塞等结果），任务异步执行既有处理链路，进度通过 WebSocket 推送
- `GET /api/upload/status/{taskId}`：查询任务进度（轮询降级用）
- **PC 端 `/api/upload` 和 `/api/upload/sse` 完全不动**

> 此方案零破坏 PC 端，代价是后端有两条上传链路（同步 + 异步）。异步链路复用现有 Service 逻辑，只是串接方式不同。

### 4.5 SecurityConfig 改动汇总

[SecurityConfig](../returnvision-backend/src/main/java/tech/jxing/returnvision/security/SecurityConfig.java) 第 75-78 行现有 permitAll 白名单需追加：

```java
.requestMatchers("/api/auth/wx-login").permitAll()
.requestMatchers("/api/auth/wx-bind").permitAll()  // 自助绑定
// /ws/** 落到 anyRequest().permitAll()，由 HandshakeInterceptor 校验
```

> **鉴权单点风险**：`/ws/**` 完全依赖 `HandshakeInterceptor` 校验 token，Spring Security 层不挡。HandshakeInterceptor 实现时**必须有单元测试覆盖**：无 token 握手被拒、伪造 token 握手被拒、过期 token 握手被拒、合法 token 握手通过 4 个场景，避免鉴权单点失效。

## 五、用户体系方案

### 5.1 策略选型：首次微信登录绑定已有账号（策略 A）

```
微信登录 -> 拿到 openid
  -> openid 在 sys_user.wx_openid 已绑定？
     -> 是：直接签发 JWT，登录成功
     -> 否：返回 1012 + bind_token，进入自助绑定页
```

**选型理由**：
1. 退运智录是内部工具，使用者已有账号，"绑一次永久免登"体验合理
2. 权限体系（ADMIN/STAFF/SUPERVISOR）零改动，微信只是多一种登录入口
3. 不依赖微信用户资料（昵称头像），与主体限制兼容
4. 登录流程对齐现有飞书 OAuth，代码结构复用

**策略 B（降级备用，未选用）**：openid 自动建号——微信登录拿到 openid 后直接创建新 sys_user（角色默认 STAFF），无需绑定已有账号。适用于"使用者无已有账号"或"策略 A 不可用"的降级场景。本项目不选用，因为退运智录是内部工具，使用者已有账号，自动建号会导致权限边界模糊（新建账号默认 STAFF，但实际可能是管理员或主管）。风险表"若最终用个人主体，策略 A 不可用，降级为策略 B"即指此策略。

### 5.2 数据库变更（已落地）

`sys_user` 表已新增字段 `wx_openid VARCHAR(64)`，加唯一索引。与现有 `feishu_user_id` 字段并列，同为 OAuth 绑定标识。

> DDL 变更已落地：[schema.sql](../returnvision-backend/src/main/resources/schema.sql) L67（CREATE TABLE 内字段）、L77（ALTER TABLE 升级已部署环境）、L78（唯一索引 `uk_sys_user_wx_openid`）；[SysUser.java](../returnvision-backend/src/main/java/tech/jxing/returnvision/model/entity/SysUser.java) L39 实体字段 `wxOpenid` 已加。[docs/05-数据库设计.md](./05-数据库设计.md) 字段说明待核对同步。

### 5.3 管理员登录

管理员绑定 openid 后也可登录小程序，但管理功能（用户/字典/审计）在小程序无入口，需回 PC 端。

### 5.4 权限矩阵（3 角色 × 5 功能）

小程序功能少，权限差异主要在"记录可见范围"。下表列各角色在小程序端的能力：

| 功能 | ADMIN | SUPERVISOR | STAFF |
|------|-------|------------|-------|
| 拍照识别 | ✅ | ✅ | ✅ |
| 人工确认（写入飞书） | ✅ 仅自己的记录 | ✅ 仅自己的记录 | ✅ 仅自己的记录 |
| 记录列表 | ✅ 全部记录 | ✅ 全部记录 | ✅ 仅自己 |
| 记录详情 | ✅ | ✅ | ✅ 仅自己 |
| 我的（个人信息/退出） | ✅ | ✅ | ✅ |

> 角色定义沿用 [docs/05](./05-数据库设计.md) `sys_role` 表，权限体系零改动。ADMIN/SUPERVISOR 在小程序端可见全部记录（便于现场核实），但管理类操作（用户/字典/审计）仍回 PC 端。

### 5.5 多端登录与数据一致性决策

- **多设备登录**：允许 PC 和小程序同时登录，不做互踢。access_token 是无状态 JWT 无法主动失效，互踢需改 refresh_token 逻辑（新登录使旧 refresh 失效），对内部工具成本不值。
- **多端数据一致性**：return_record 按 `user_id` 隔离，小程序用户只看自己的记录；PC 端管理员查看为主，不会与小程序用户同时改同一字段。并发概率极低，按最后写入为准，不引入乐观锁/版本号。

### 6.4 鉴权拦截器差异说明

PC 端 [api.js](../returnvision-frontend/src/api.js#L20-L66) 有 refresh token 并发刷新合并逻辑（基于 axios 拦截器）。小程序端 `uni.request` 拦截器机制不同，**并发刷新合并逻辑需基于 uni.request 封装重写**，不能直接搬 axios 代码。功能目标一致：401 时用 refresh_token 刷新，并发请求合并为一次刷新。

**并发刷新伪代码**（基于闭包缓存 `isRefreshing` flag + pending 队列）：

```js
let isRefreshing = false
let pendingQueue = []  // 等待刷新完成的请求队列

function request(options) {
  return new Promise((resolve, reject) => {
    uni.request({
      ...options,
      success: (res) => {
        if (res.statusCode === 401 && !options._isRetry) {
          if (isRefreshing) {
            // 已在刷新中，入队等待
            return pendingQueue.push({ resolve, reject, options })
          }
          isRefreshing = true
          // 当前请求也入队，等刷新完成后统一重放（不能立即重放，此时 token 还没刷新会再次 401）
          pendingQueue.push({ resolve, reject, options })
          // 调刷新接口
          refreshToken().then(() => {
            // 刷新成功，重放队列（含当前请求）
            pendingQueue.forEach(({ resolve, reject, options }) => {
              request({ ...options, _isRetry: true }).then(resolve).catch(reject)
            })
            pendingQueue = []
          }).catch(() => {
            // 刷新失败，清空队列，跳登录页
            pendingQueue.forEach(({ reject }) => reject(new Error('登录已过期')))
            pendingQueue = []
            clearTokenAndRedirectLogin()
          }).finally(() => { isRefreshing = false })
        } else {
          resolve(res)
        }
      },
      fail: reject
    })
  })
}
```

> 关键点：`_isRetry` 标记防刷新后的请求再次触发 401 死循环；刷新失败则清空队列并跳登录页。

### 6.5 图片处理与基础库兼容

**图片处理**：
- **EXIF 方向矫正**：手机拍照常有方向旋转（90°/180°/270°），直接送 OCR 准确率下降。上传前用 `uni.getImageInfo` 读取 orientation，必要时用 canvas 旋转矫正。
- **压缩参数**：`uni.compressImage` quality 60-80，目标 500KB 内；压缩失败兜底用原图（不阻塞上传）。
- **原图保留**：不保留原图（节省 COS 存储），只存压缩后版本。

**基础库兼容**：
- `manifest.json` 配置最低基础库版本 **2.10.0**（`uni.chooseMedia` 最低要求）。
- 低版本兜底：`uni.chooseMedia` 不支持时降级 `uni.chooseImage`（API 差异：chooseImage 回调是 `tempFilePaths` 数组，chooseMedia 是 `tempFiles` 数组，需适配）。

## 八、部署变更

### 8.1 Nginx 加 WebSocket 反代

现有 [deploy/nginx/user_conf.d/default.conf](../deploy/nginx/user_conf.d/default.conf) 配的是 SSE。WebSocket 需加 `Upgrade`/`Connection` 头：

```nginx
location /ws/ {
    proxy_pass http://backend:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
}
```

> **access_token 日志脱敏**：WebSocket 握手 token 走 query 参数（见 4.2 节鉴权说明），默认 access_log 会记录完整 URL 含 token。需在 nginx.conf 的 http 块定义不含 query 的 log_format，并在 /ws/ location 用 `access_log` 指定该格式。示例：`log_format ws_safe '$remote_addr - $remote_user [$time_local] "$request_method $uri" $status $body_bytes_sent';`（用 `$uri` 不用 `$request`，不记 query）。

### 8.2 服务器域名白名单（小程序后台配置）

`returnvision.jxing.tech` 需在小程序后台配置为：
- request 合法域名（uni.request）
- uploadFile 合法域名（uni.uploadFile）
- socket 合法域名（uni.connectSocket，需 wss）

已 HTTPS，满足要求。

## 十一、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| `/api/upload` 改造破坏 PC 端 | PC 端上传失效 | 已确认 PC 端在用；新增 `/api/upload/async` 不改原接口 |
| 主体限制导致无法用个人主体发布 | 小程序无法上架 | 开发期用个人 AppID；发布前办个体工商户；登录策略 A 依赖企业主体 |
| 若最终用个人主体，策略 A 不可用 | 登录流程要改 | 降级为策略 B（openid 自动建号），但需重设计权限边界 |
| WebSocket 连接稳定性 | 弱网下断连 | 心跳 30s + 自动重连 3 次 + 轮询降级 |
| 服务重启任务丢失 | 用户需重拍 | 内存方案接受丢失（单次 5-15s，重启概率低）；未来升级 Redis |
| 小程序包体积 | 超限无法发布 | 核心链路无 echarts，包体积无压力 |
| 微信审核驳回 | 延迟上线 | 类目选对，功能说明写清，隐私协议配齐；预留多次提审时间 |
| 手机拍照图片过大 | 上传慢/耗流量 | 前端上传前压缩（uni.compressImage），控制到 500KB 内 |
| 仓储现场弱网/断网 | 上传 COS 失败、WebSocket 断连 | 上传失败提示重试；不本地暂存队列（复杂度高，业务量小不值得，后续扩规模再议） |
| 生产排障缺监控 | 出问题无法定位 | 小程序端用 `App.onError` + 自定义日志接口上报业务错误；后端 WebSocket 暂用日志（连接数/推送失败/taskStore 内存），后续引入 Prometheus |
